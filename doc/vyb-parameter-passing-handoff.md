# Clarify Vyb parameter passing and ownership

Please add a concise paragraph to `README.md` and a focused “Parameter passing” section to `docs/refman/PROGRAMMERS_GUIDE.md`. The goal is to make value passing, borrowed reference passing, and ownership unmistakable without introducing a new `ref()` spelling. Work only in the Vyb language repository; do not modify VybForge or VybOS. Inspect the current implementation and tests first, since the observations below came from a source review, not an executed conformance suite.

Explain that plain `x<T>` parameters have value semantics rather than aliasing the caller’s variable. Distinguish copying a value from recursively duplicating everything it references: copied shared handles can still refer to the same object. In the ordinary function-entry code reviewed in `src/vre/llvm/cgen_decl.cpp`, Vec parameters are deep-copied, owning structs use ownership-aware copying, Strings retain their backing buffers, and non-primitive `our<T>` parameters retain their shared control blocks. Verify these behaviors before documenting them, and describe their practical consequences, including the cost of passing large vectors by value.

Explain the existing reference-passing vocabulary: `their<T>` is a non-owning borrowed reference, `borrow(value)` supplies mutable access, and `view(value)` supplies read-only access using the actual supported const-qualified type syntax. Include a minimal, runnable example contrasting a plain Counter parameter with `increment(c<their<Counter>>)` called as `increment(borrow(counter))`, showing which mutations are visible to the caller. Keep ownership separate: `my<T>` expresses unique ownership and `our<T>` expresses shared ownership; neither is merely another spelling of `ref`. Also distinguish mutating the referenced object from reassigning the callee’s local handle or replacing the caller’s variable.

Before promising unique-ownership transfer at function boundaries, investigate a specific discrepancy: the guide describes `my` transfers as moves, while comments and cleanup paths in `src/vre/llvm/cgen_expr.cpp` describe `my` parameters as non-freeing borrows and release fresh temporary owners after calls. Determine actual behavior for named owners and temporaries, including caller usability after the call and exactly-once cleanup. Likewise, the reviewed `their(x)` constructor branch merely passes through an evaluated value, whereas `borrow(x)` has dedicated address-taking lowering; do not document those expressions as interchangeable. If these are implementation gaps rather than stale comments, report them explicitly and propose a scoped follow-up instead of silently choosing or changing the language contract.

Validate the documentation with focused tests for plain values, mutable borrows, immutable views, unique owners, and shared owners. Cover caller-visible mutation, parameter reassignment, lifetime/escape restrictions, and cleanup, using primitives, structs, vectors, and nested fields. Check representative ordinary, generic, bind-method, and closure call paths rather than assuming their lowering is identical. Deliver the short README overview, the precise guide section with tested examples, and a brief account of verified behavior versus remaining discrepancies. Keep this a documentation-and-conformance task, not an ownership redesign or a new reference API.
