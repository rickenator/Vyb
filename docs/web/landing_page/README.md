# vyb-lang.org — the deployed project site

`index.html` in this directory **is** the live root page of
<https://vyb-lang.org/>. A GitHub push does not publish it: the page is copied
to the web host (see *Deploy* below). The site is separate from the repo, so a
change lands in the repository and in production independently.

## What is in the page

Two layers, and only one of them is generated (`build_page.py`):

* **Shell** (hand-maintained, at the top and bottom of `index.html`): `<head>`
  metadata — description, canonical, Open Graph, Twitter card, JSON-LD — the
  topbar, the hero with the inline logo, the footer, and the copy-button script.
* **Body** (generated): the whole "Vyb Programming Guide" section is a render of
  the repository [`README.md`](../../README.md), plus the sidebar table of
  contents built from the body's `h2`/`h3` headings. Heading ids are
  GitHub-style slugs with the `#` anchor links the stylesheet styles, and
  repo-relative links are rewritten to GitHub `blob/main` URLs so they work for
  a reader who has no checkout.

That is why the page's feature list, version, test count and platform claims are
the README's: **update the README first**, then regenerate the body. The page's
non-README facts (site name, canonical host, Aniviza attribution) live in the
shell only.

## Regenerating the body from README.md

The body and the sidebar are regenerated by `build_page.py` (needs
`markdown-it-py`, nothing else); the shell is never touched by it:

```bash
python3 build_page.py           # rewrite index.html in place
python3 build_page.py --check   # exit 1 if index.html is out of date
```

`index.html` carries four markers — `<!-- BODY:BEGIN -->` / `<!-- BODY:END -->`
inside `<main>` and `<!-- TOC:BEGIN -->` / `<!-- TOC:END -->` in the `<aside>`.
Everything between them is generated; everything outside is shell. The script

1. renders the README as GitHub does — GFM tables, fenced code, and CommonMark
   list continuation, so a fenced block indented inside a list item stays inside
   that item (python-markdown flattens those and emitted stray `<p><code>`
   blocks for the whole *Feature highlights* list);
2. gives every heading a GitHub-style slug id (lowercase, punctuation dropped,
   spaces → `-`, duplicates get `-1`, `-2`) plus the `#` anchor link;
3. rewrites repo-relative links to `https://github.com/rickenator/Vyb/blob/main/<path>`
   (directories → `tree/main/`), and opens external links in a new tab;
4. rebuilds the sidebar TOC from the `h2`/`h3` headings in document order.

After a run, re-check: every TOC link and heading anchor resolves to an existing
id, there are no duplicate ids, and the version and test count in the page match
the README (the shell carries neither — `deploy.sh` greps the *test count* as its
deploy token, so update `TOKEN` there when the suite grows).

### Family links in the shell

The footer lists the sibling projects (VybOS, VybWin, VybForge, VybFly) and the
hero names them. Those are shell, not README, content: keep them in `index.html`
when a project is added or renamed.

## Deploy

```bash
./deploy.sh            # upload + verify the live site
./deploy.sh --check    # verify only (no ssh)
```

* Host: `anivizac@69.89.24.177` (Bluehost), ssh on port 2222. The document root
  is `/home4/anivizac/vyb/` (confirmed 2026-10-27 — **not** under
  `public_html`), which is what `DEST` defaults to; override it if a future move
  makes the check report the wrong root (`--check` greps the live page for the
  current test-count token, so a stale upload or a wrong root cannot pass as
  success).
* Auth: the key that works is `~/.ssh/anivizac_key` **on apex**, not on godzilla.
  godzilla's `~/.ssh/id_ed25519_aniviza` is still **not authorised** on the host
  and there is no SSH password here, so the working flow is: `rsync` this
  directory to `apex:/tmp/vyb-lang-deploy/` and run
  `DEPLOY_KEY=$HOME/.ssh/anivizac_key ./deploy.sh` there. On a fresh host,
  seed apex's `~/.ssh/known_hosts.vyb-lang` first with
  `ssh-keyscan -p 2222 -t ed25519 69.89.24.177` (strict checking is on, and the
  old entry is stale). Alternatively authorise godzilla's key in cPanel (SSH
  Access → Manage SSH Keys → Import the `.pub` half → Authorize), or upload
  through cPanel → File Manager without ssh.
* Two host quirks the script handles: offering every key in the ssh agent gets
  the connection dropped with "Too many authentication failures" (so exactly one
  identity is offered), and the host's ssh host key changed since the stale
  `known_hosts` entry, so the script bypasses that entry rather than trusting
  it.
* Every asset the page references must be uploaded with it. `/vyb.png` (the
  `og:image` / `twitter:image`) was **missing** from the live root and 404'd, so
  social previews showed no image; the script now sends it and asserts it
  resolves after upload. Case matters on the host even where the authoring
  machine is case-insensitive.
* The live root is a distinct directory from `aniviza.com`'s document root
  (`/favicon.ico` differs between the two, and `/bdas.html` 404s here), so the
  Aniviza deploy script does not publish this page.
